# Guia de upgrade da versão 2.0

A versão 2.0 adicionou muitas funcionalidades poderosas. Se você já investiu em um projeto para uso comercial e criou um projeto de application na versão 1.1 baseado no projeto Skeleton fornecido oficialmente, você pode ajustar seu projeto Skeleton de acordo com os pontos a seguir. Se você é um novo projeto, siga a documentação para criar um novo projeto através do comando `composer create-project hyperf/hyperf-skeleton` para usar a nova versão 2.0 do código do skeleton. Se você está usando atualmente uma versão inferior a 1.1, então você precisa primeiro atualizar para a 1.1 e depois atualizar para a 2.0 de acordo com este guia de upgrade.

## Atualize o Swoole para 4.5+

A versão 2.0 elevou a exigência mínima de versão do Swoole de 4.4+ para 4.5+. Existem algumas diferenças nos detalhes de uso entre as duas versões. O Hyperf se adaptou a essa diferença de versão em versões anteriores, então você pode ignorar os detalhes da diferença. Atualizar a versão do Swoole para 4.5+ é principalmente para reduzir o impacto de longo prazo do legado histórico no Hyperf. Você pode verificar a versão do Swoole no ambiente atual executando `php --ri swoole`. Você pode concluir o upgrade do Swoole de acordo com a [documentação do Swoole](https://wiki.swoole.com/#/environment).

## Adicionando a inicialização do ClassLoader no arquivo de entrada

A 2.0 mudou a lógica interna do AOP, então você precisa adicionar uma linha de código de inicialização no arquivo de entrada do framework `bin/hyperf.php`. Você precisa adicionar o código `Hyperf\Di\ClassLoader::init();` na primeira linha da função anônima de entrada, como segue:

```php
<?php

ini_set('display_errors', 'on');
ini_set('display_startup_errors', 'on');

error_reporting(E_ALL);
date_default_timezone_set('Asia/Shanghai');

! defined('BASE_PATH') && define('BASE_PATH', dirname(__DIR__, 1));
! defined('SWOOLE_HOOK_FLAGS') && define('SWOOLE_HOOK_FLAGS', SWOOLE_HOOK_ALL);

require BASE_PATH . '/vendor/autoload.php';

// Self-called anonymous function that creates its own scope and keep the global namespace clean.
(function () {
    Hyperf\Di\ClassLoader::init();

    /** @var \Psr\Container\ContainerInterface $container */
    $container = require BASE_PATH . '/config/container.php';

    $application = $container->get(\Hyperf\Contract\ApplicationInterface::class);
    $application->run();
})();

```

Ao mesmo tempo, o arquivo de entrada do PHPUnit pode precisar da mesma alteração, localizado em `tests/bootstrap.php`, assim:

```php
<?php

declare(strict_types=1);

error_reporting(E_ALL);
date_default_timezone_set('Asia/Shanghai');

! defined('BASE_PATH') && define('BASE_PATH', dirname(__DIR__, 1));
! defined('SWOOLE_HOOK_FLAGS') && define('SWOOLE_HOOK_FLAGS', SWOOLE_HOOK_ALL);

Swoole\Runtime::enableCoroutine(true);

require BASE_PATH . '/vendor/autoload.php';

Hyperf\Di\ClassLoader::init();

$container = require BASE_PATH . '/config/container.php';

$container->get(Hyperf\Contract\ApplicationInterface::class);

```

## Ajuste o `composer.json`

Devido ao ajuste da lógica interna do AOP na versão 2.0, o script `init-proxy.sh` foi removido, então você precisa remover a instrução de execução do `"init-proxy.sh"` em `scripts.post-autoload-dump` do `composer.json`, e modificar o comando em `post-autoload-dump` para a instrução `rm -rf runtime/container`.

```json
{
    "scripts": {
        "post-root-package-install": [
            "@php -r \"file_exists('.env') || copy('.env.example', '.env');\""
        ],
        "post-autoload-dump": [
            "rm -rf runtime/container"
        ],
        "analyse": "phpstan analyse --memory-limit 300M -l 0 -c phpstan.neon ./app ./config",
        "cs-fix": "php-cs-fixer fix $1",
        "start": "php ./bin/hyperf.php start",
        "test": "co-phpunit -c phpunit.xml --colors=always"
    }
}

```

## Ajuste a versão de dependências do composer.json

Como queremos atualizar para a versão 2.0 dos componentes, e o projeto skeleton original depende por padrão da versão 1.1.x dos componentes, precisamos fazer alguns ajustes nas restrições da dependência, alterando as dependências de todos os componentes Hyperf originais de `~1.1.0` para `~2.0.0`, e você também precisa modificar a dependência de versão do `phpstan/phpstan` para `^0.12`. Após a modificação, você precisa executar `composer update` para atualizar as dependências para a versão 2.0.

## Ajuste o Dockerfile

Durante o processo de empacotamento da imagem Docker, executar ativamente o comando `php bin/hyperf.php` ajudará a criar antecipadamente todas as classes proxy e caches de varredura de annotations que precisam ser gerados, para que não seja necessário varrer novamente quando o ambiente de produção for iniciado, o que pode otimizar enormemente o tempo de inicialização em produção e o uso de memória. Os exemplos a seguir não contêm o código não modificado do Dockerfile.

```dockerfile
ENV TIMEZONE=${timezone:-"Asia/Shanghai"} \
    APP_ENV=prod \
    SCAN_CACHEABLE=(true)

COPY . /opt/www
RUN composer install --no-dev -o && php bin/hyperf.php

EXPOSE 9501

ENTRYPOINT ["php", "/opt/www/bin/hyperf.php", "start"]
```

Para usuários que não fazem deploy via `Docker`, deve-se observar que, antes de reiniciar o serviço, é melhor executar `php bin/hyperf.php` e depois reiniciar o serviço para reduzir o tempo de reinicialização.

## Ajuste o arquivo de configuração config/config.php

Você precisa adicionar dois itens de configuração, `app_env` e `scan_cacheable`, à configuração em `config/config.php`. O exemplo de código a seguir não contém outros conteúdos de configuração irrelevantes, como mostrado abaixo:

```php
<?php

return [
    // The production environment uses the prod value
    'app_env' => env('APP_ENV', 'dev'),
    // Whether to scan the cache with annotations
    'scan_cacheable' => env('SCAN_CACHEABLE', false),
];
```

A configuração `scan_cacheable` é usada para controlar se as annotations devem usar o cache de varredura quando a application inicia. Existem modificações relacionadas no `Dockerfile` e no `config/config.php` acima. Quando o valor dessa configuração é `true`, quando o projeto inicia, ele considerará que todas as classes já foram varridas e os caches e proxies correspondentes já foram gerados corretamente, e a fase de varredura será ignorada para otimizar o tempo de inicialização e reduzir o overhead de memória.

## Modifique `config/autoload/logger.php`

Como a versão 2.0 atualizou a versão que depende do Monolog, nas versões mais recentes do Monolog o formato de log padrão mudou. Se houver requisitos para o formato do log, como a necessidade de conectar com o sistema de logs de acordo com o formato do log, você pode modificar o item de configuração `dateFormat` do arquivo de configuração `config/autoload/logger.php` para manter a consistência com a versão anterior.

```php
<?php

declare(strict_types=1);

return [
    'default' => [
        'handler' => [
            'class' => Monolog\Handler\StreamHandler::class,
            'constructor' => [
                'stream' => BASE_PATH . '/runtime/logs/hyperf.log',
                'level' => Monolog\Logger::DEBUG,
            ],
        ],
        'formatter' => [
            'class' => Monolog\Formatter\LineFormatter::class,
            'constructor' => [
                'format' => null,
                'dateFormat' => 'Y-m-d H:i:s',
                'allowInlineLineBreaks' => true,
            ],
        ],
        'processors' => [
        ],
    ],
];

```

## Modifique `config/autoload/exceptions.php`

A versão 2.0 ajustou a lógica de tratamento dos comportamentos de exceção de roteamento HTTP, como rota não encontrada (404), método de requisição não correspondente (405), etc., e passou a lançar uma subclasse de exceção de `Hyperf\HttpMessage\Exception\HttpException`. Em seguida, o ExceptionHandler é usado para gerenciar de forma unificada essas exceções e tratar as respostas correspondentes, para que os usuários também possam obter uma experiência consistente de retorno de resposta ao lançar exceções correspondentes. Porém, como o ExceptionHandler é um mecanismo gerenciado pelo usuário, por padrão na versão 1.1 o Skeleton configura uma classe `App\Exception\Handler\AppExceptionHandler` para tratar a exceção e retorná-la ao cliente com o status code 500, então você precisa usar o `Hyperf\HttpServer\Exception\Handler\HttpExceptionHandler` fornecido pela versão 2.0 para tratar o HttpException, configurando-o no arquivo de configuração `config/autoload/exceptions.php`, e certificando-se de que ele esteja antes da configuração `App\Exception\Handler\AppExceptionHandler`. O exemplo de configuração a seguir omite configurações irrelevantes, como mostrado abaixo:

```php
<?php
return [
    'handler' => [
        'http' => [
            Hyperf\HttpServer\Exception\Handler\HttpExceptionHandler::class,
        ],
    ],
];
```

Após concluir a configuração do ExceptionHandler, você pode acessar diretamente uma rota que não existe. Se o status code da resposta for `404`, pode-se entender que a modificação dessa configuração foi concluída.

## Modifique o client gRPC

Para evitar conflitos de nomenclatura com o negócio real do gRPC, a versão 2.0 ajustou a nomenclatura das funções da classe base do client gRPC.

* `simpleRequest` -> `_simpleRequest`
* `clientStreamRequest` -> `_clientStreamRequest`
* `getGrpcClient` -> `_getGrpcClient`

Além disso, alguns métodos que não deveriam ser expostos se tornaram métodos privados. Se seu client gRPC envolve a chamada dos métodos acima, por favor ajuste a nomenclatura.

## Remova o listener de lazy load do DI

Se seu projeto usa a função de lazy loading dos componentes DI, você precisa registrar um listener `Hyperf\Di\Listener\LazyLoaderBootApplicationListener`, mas na versão 2.0, esse listener foi removido, você pode usar essa funcionalidade diretamente. Então, se você usou essa funcionalidade anteriormente, precisa remover o registro do listener em `config/autoload/listeners.php`;

## Vincule a relação NormalizerInterface

Quando você usa a funcionalidade JSONRPC e usa a biblioteca `symfony/serializer` para fornecer funções de serialização, como a versão 2.0 não mapeia mais automaticamente a classe de implementação de `Hyperf\Contract\NormalizerInterface`, você precisa adicionar manualmente a relação de mapeamento, como segue:

```php
use Hyperf\Utils\Serializer\SerializerFactory;
use Hyperf\Utils\Serializer\Serializer;

return [
    Hyperf\Contract\NormalizerInterface::class => new SerializerFactory(Serializer::class),
];
```

## Ajuste a classe de implementação de Hyperf\Contract\ProcessInterface

O método `isEnable` em `Hyperf\Contract\ProcessInterface` adicionou um parâmetro `$server`, `isEnable($server): bool`. Todas as classes de implementação de ProcessInterface exigem que você faça alguns ajustes nesse método.

## Verifique o arquivo config/autoload/aspects.php

Se você já fez algumas operações de emagrecimento no Skeleton anteriormente, você precisa verificar se o arquivo `config/autoload/aspects.php` existe. Se não existir, você precisa adicionar um arquivo e retornar um array vazio.

> Esse problema será corrigido na 2.0.1, então essa verificação não será necessária no futuro.

## Verifique o collector de annotations personalizadas

Se você usa annotations personalizadas e usa um collector `Collector` personalizado para coletar metadados de annotations, você precisa configurar o `Collector` correspondente em `annotations.scan.collectors`, porque em modo de desenvolvimento, será determinado com base no horário de modificação do arquivo se o arquivo foi modificado, e então decidirá se deve recoletar os metadados de annotations correspondentes. Então, quando `annotations.scan.collectors` não estiver configurado, isso fará com que as annotations só tenham efeito quando o `server` for iniciado pela primeira vez.

Como na camada de application, a configuração está localizada no arquivo `config/autoload/annotations.php`, como segue:

```php
<?php

return [
    'scan' => [
        'collectors' => [
            CustomCollector::class,
        ],
    ],
];
```

Para componentes, a configuração é fornecida pelo ConfigProvider, como segue:

```php
<?php

return [
    'annotations' => [
        'scan' => [
            'collectors' => [
                CustomCollector::class,
            ],
        ],
    ]
];
```

## Inicie o serviço e teste a interface de acesso

Ao usar o Swoole 4.5 e o componente view, se houver um problema com a interface 404, você pode tentar excluir o item de configuração `static_handler_locations` no arquivo `config/autoload/server.php`.

Os caminhos sob essa configuração serão considerados rotas de arquivos estáticos, então se `/` for configurado, isso fará com que todas as interfaces sejam consideradas caminhos de arquivo, resultando em 404 nas interfaces.

## Concluindo o upgrade

Neste ponto, o upgrade da versão 2.0 foi concluído, mas como cada arquivo interno do Hyperf pode ser sobrescrito através de DI, se você sobrescreveu alguns arquivos internos do framework ajustados neste upgrade, ainda precisará fazer alguns ajustes de acordo com a situação real.

Se você encontrar algum problema durante ou após o upgrade, por favor, acesse o [Github Issue](https://github.com/hyperf/hyperf/issues) para enviar seu issue, explicando o problema que você encontrou, e tentaremos ajudá-lo o mais rápido possível.
